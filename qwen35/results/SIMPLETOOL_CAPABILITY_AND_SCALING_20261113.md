# SimpleTool 本轮能力、分数优化与 Scaling 证据报告

整理日期：2026-11-13。质量结果截至 2026-11-12；本报告重新读取现有逐题评分、运行回执与冻结数据，未启动新训练或推理。面向研究、产品与 infra 协作方，可与速度工作线的报告配套使用。

## 1. 当前结论与可引用范围

本轮已经完成从工具协议对齐、公开套件复测，到中英反事实诊断、数据比例扩展、模型尺寸扩展及 FP8 数值故障修复的能力验证。质量主表覆盖 **7 个尺寸、20 个“尺寸×数据批次”配置，每配置同一套 800 题，共 16,000 次完整调用质量判定**；另有公开来源 4,786 行的 12 组同口径新旧/精度对照。

主要结果如下：

- **参数/基座规模扩大有效。** 5% 训练版本在诊断集上的完整调用分数，从 0.8B 的 37.625%，经 2B 47.0%、4B 65.0%、9B 68.875%、35B-A3B 80.375%、122B-A10B 83.5%，达到 397B-A17B 的 85.25%。这是已测配置中的整体上升趋势。
- **当前数据配方出现边际收益平台。** 2B 的 5%→20%→50% 为 376→377→375/800；4B 的 5%→20% 为 520→518；9B 为 551→546。0.8B 从 5% 到 20% 仍提高 33 题，随后到 50% 回落 9 题。继续扩大同类数据，没有稳定带来更多总分。
- **大模型还不能宣布在 5% 饱和。** 35B、122B、397B 从 0.5% 到 5% 仍分别提升 69、47、37 题；缺少其 20%/50% 对照。5% 是当前有证据支持的预算基准，并非普遍最优训练量。
- **基础工具选择已较强，困难集中在参数。** 5% 大模型的函数名正确率为 98.25%–99.0%，完整调用为 80.375%–85.25%。高难变换、数组对齐、实体角色绑定、状态恢复仍保留明显空间。
- **部署和能力已有独立证据。** 手机 MLX 多分支、云端 vLLM 并行 decode 与共享前缀均已运行验证；397B FP8 权重配 BF16 计算完成 800 题回归。最新单 H200 的 35B-A3B 接近 16Hz 来自用户/速度工作线报告，本文不替代其计时回执。397B 在 8×H200 达到类似频率仍是待测目标。

本文使用“完整调用正确”指函数名及全部必填参数同时正确，不指工具已执行成功。数据与模型 scaling 是观测趋势，未拟合幂律，也未把各批次当作严格单变量实验。

## 2. SimpleTool 的工作方式与本轮任务边界

模型共享同一套 Transformer/混合递归 backbone，以特殊 token 区分八个逻辑分支：`content`、`function`、`arg1`…`arg6`。它们不是八个独立完整模型，也不是先生成函数名再串行生成参数。

```text
公共输入 = system + tools definition + history + environment + query
                         ↓ 公共 prefill / 可复用状态
          ┌──────────────┼──────────────────┐
       function        arg1 … arg6         content（本轮质量评测不生成）
          └──────────────┴──────────────────┘
                 按所选函数 schema 组装一次调用
```

每个分支仍独立自回归生成，直到自身 closing marker。并行开始时，参数头看不到 function 头刚生成的结果；它们需要由共同输入独立推断同一个函数、对象和参数绑定。相应地，分支间一致性是重要质量指标。

参数约定是位置绑定：工具 schema 的必填属性在前，`required` 列表与属性顺序一致，`arg1`、`arg2` 等按该顺序解释。工具候选可以有多个；本轮每题仅要求一个调用。多参数测试包含 4、5、6 个顶层参数，一个参数可为对象或数组，因此可以生成超过六个叶子字段。

初始需要的 head 数按**所有候选 schema 的最大 arity**确定，不读取答案。函数确定后，只解释其 schema 所需槽位，额外尾头不影响主分数。零参数函数仍需要 function 头，不要求凭空制造 arg1。当前报告不涵盖一个请求里的多个连续工具调用、实际环境闭环、机器人真机成功率或 watcher 策略。

## 3. 本轮“分数优化”实际包含哪些变化

### 3.1 输入协议修正：让评测遵守模型的训练契约

早期 Mobile Actions 输入直接保留原始 `properties` 与 `required` 的顺序，未统一必填前置。虽然当时输入映射与评分映射内部一致，却不符合 SimpleTool 的训练约定。

真实 fixture 审计：640 条单调用中，参考所选工具仅 367 条符合约定，273 条不符合；全部 6,727 个候选定义中有 2,151 个不符合。应区分“273 条所选工具违规”和“整个 prompt 内至少一个候选违规”。后一项在含多调用的 961 条全量 prompt 中为 953 条。

典型修正：`create_contact(email, last_name, first_name, phone_number)` 改为 `create_contact(first_name, last_name, email?, phone_number?)`；同步修改 properties、required、arg 映射及评分解释。`create_calendar_event` 使用一致的 `title, datetime` 顺序。

这是输入协议修复，不是模型通过更多训练突然学会了任意参数排列。旧随机顺序分数不能与新规范顺序分数合并为训练收益；也没有把旧预测重新排列后伪装成模型重跑结果。

### 3.2 指标修正：按业务所需的调用判定

主指标只要求所选函数名和全部必填参数正确。选中函数只有两个必要参数时，其余无用尾头不影响判定；这是对有效调用的定义，不是将必要参数答错的样例放宽。所有缺失、格式错误和截断仍保留在分母内。

同时独立报告函数名、schema 有效、配对联合正确及各能力切片，避免高函数名分数遮住参数错误。公开套件采用冻结的 acceptable-value matcher，自建 800 采用严格类型及字面值匹配，两种分数分表呈现。

### 3.3 真正的训练增益：固定题集和评分后再比较

4,786 行公开来源对照已经让 0.5% 与 5% 使用同样的候选、规范参数顺序、过滤和评分。该表中的新旧差异才可用于讨论本轮训练配方的增益。800 题也保持相同输入标签与评分，但不同训练代际的 empty-think 前缀及训练配置有差异，仍非严格单因素消融。

### 3.4 数值故障修复：恢复有效能力，而不是给模型“补分”

397B 的 FP8 权重曾在 FP16 计算下输出乱码。最终通过固定权重和输入逐层追踪，发现共享专家中间结果溢出 FP16 范围；改为 BF16 计算后完成全量回归。失败的乱码 run 保留为 infra 失败证据，不用其 0/800 描述训练能力。详细数值与对照见第 11 节。

交付 LoRA 时，需要同时保留 `head_tokens.safetensors` 与 tokenizer；17 个特殊 token 对应八组起止标记及 null。仅 adapter 不包含全部训练结果。推理时必须从实际 tokenizer 解析 marker，不硬编码 token ID。

## 5. Benchmark：SimpleTool Diagnostic 800

### 5.1 构成、语言与能力目标

| 批次 | 题数/语言 | 能力家族及各题数 | 重点 |
|---|---|---|---|
| cf-zh | 200 中文 | environment / history / binding / semantics，各50 | 状态微变、伪多轮、实体绑定、语义 |
| cf-en | 200 英文 | 同四家族，各50 | 独立英文构造，并非中文翻译 |
| hard | 100中文+100英文 | environment / history / binding / logic / transformation，各40 | 多约束、边界、依赖、计算变换 |
| multiarg | 100中文+100英文 | joins / roles / history / arrays / transformation，各40 | 4–6参数，关联、角色、平行数组、状态、变换 |

总计 400 中文、400 英文。四批各 200，故总体为四切片等权；不能拿它与公开套件行数加权总分直接比较。

### 5.2 反事实配对与伪多轮

800 行构成 400 对，其中 370 对输入变化要求调用改变，30 对为结果应保持的 invariant 控制。按冻结 tokenizer 检查，309/400 对的 prompt token 编辑距离为 1；其余仍是小编辑，不声称所有对都只差一个 token。

配对联合正确要求两侧调用都正确。仅输出发生变化不算通过；仅 invariant 两侧输出相同，也可能是两侧都错。history 是给定历史记录，模型只生成下一次调用，未进行实时外部多轮执行。

每条都包含 tags、objective、rationale、expected；这些字段用于审计/评分，**不进入模型 prompt**。英文为独立任务，不是简单翻译。多参数组的 4/5/6 参数题数分别为 68/68/64；分组题目不同，不能仅凭分数差异推断增加一个参数造成多少损失。

### 5.4 生成与评分

- 质量推理 temperature=0、seed=1107、每头最多128 tokens；不生成 content，不发图片，不执行工具。逐头独立终止。
- 早期 0.8B/2B/4B 的 0.5% 和 5% 使用历史 direct-head 前缀；新代模型按训练导出契约插入一次 `<think>\n\n</think>\n\n` 后接 head。完整主表的 `protocol` 记录在附件。
- 自建套件严格核对函数名及全部必填参数。字符串按 head 原文解释；其他类型要求合法 JSON；布尔不等同数字；数组顺序/重复保留；对象 key 顺序不影响结果。重复 key、非有限数值等非法 JSON 不接受。
- 只解释所选函数的参数槽位，额外尾头忽略；本套 800 题中 `required_correct` 与 `exact_correct` 实际逐行相同。
- schema 有效只描述形状/类型，不代表值正确；正常 closing 只描述解码终止，不代表 schema 有效。
- 自建评测主要使用 vLLM 0.33 eager、prefix caching。缓存开启不等于物理 prefill 只计算一次，也不证明所有头命中100%。各 run 的 dtype、TP、输入 token manifest 与输出均保留。
- 该数据为 agent 辅助合成并做确定性验证，未做独立盲评真实流量抽样。题目配对相关，不是800个独立 IID 样本；没有多训练 seed 误差条。

**早期增量确实有效。** 0.8B/2B 从0.5%到5%各提高105/123题；35B也提高69题。增加同类数据帮助模型学会当前输出契约、参数映射与任务模式。

**继续堆量已出现平台。** 2B 5%之后只在375–377题波动；4B 5%→20%少2题；9B少5题。0.8B平台出现更晚，在20%后回落。不能把这些小变化解读为确定退化或训练发散，因为无多seed、配方也不完全一致。

**平台不是测试集满分天花板。** 2B仍有超过一半题不正确；4B/9B也分别有280/249题错误。因此不可能仅以“分数已接近100%”解释这些平台。更符合现有证据的说法是：当前训练数据分布、配方、基础能力与高难测试需求之间存在边际收益递减。数据质量、困难类型覆盖、状态/角色绑定监督和训练目标仍可能带来收益。

**基础子集与高难子集要分开。** 397B5%的中英基础为95%/97.5%，确有局部天花板；高难72%、多参数76.5%，仍有实质改进空间。122B的多参数甚至更高，为79.5%，说明局部能力不随尺寸严格单调。

现阶段可以把5%作为多数尺寸的高性价比起点，而不能声称“5%已经让所有尺寸数据饱和”。继续投入应针对独立验证集上的残余错误，而非把这800题的答案回灌训练再用同一套分数论证泛化。

## 11. 精度与推理可靠性：397B FP8修复

397B的有效部署为 **FP8 block权重 + BF16计算**。保持checkpoint、LoRA、special-token和tokenizer不变，调整运行计算dtype，attention KV为auto/BF16；FP8矩阵算子仍在执行，没有把权重全部退回BF16。

同一固定输入逐层追踪：FP16路径在rank3的第26层 `shared_expert.down_proj` 输出首次产生Inf，其余rank在同层输出出现异常。BF16同位置幅度113664，另一层68096，均超过FP16最大有限值65504；BF16路径8rank所测边界均有限。另从启动强制Triton的FP16对照仍失败，因此不能仅归咎于某个Cutlass backend。

|---|---|---|---|---|---|---|---|

## 14. Infra已证明的事项与速度工作线接口

本节只保留解释能力落地所需的infra证据，不把质量批跑的运行时间解释成性能上限。

### 14.1 手机与云端的执行方式

手机MLX线已让0.8B/2B/4B四头、八头模型运行：packed INT4、W4A16、量化attention KV8、GDN/门控等稳定性敏感路径保留所需浮点精度；GPU真实batch并行，前缀共享，fork后递归状态独立，每头独立停止。模型/状态生命周期、串行推理lane及内存锁等工程边界已整理在端侧infra交付目录。

本文质量表是云端vLLM结果，小模型attention KV默认FP16、大模型按实际dtype记录，不能把它们统称“手机W4A16+KV8实测质量”。也不能将旧手机权重的速度与新训练权重分数拼成同一配置的一行。

Qwen3.5混合结构的可复用状态不止attention KV，也包含GDN递归状态；分支fork后必须隔离可变状态，不能跨head串写。

### 14.2 已有4090解码隔离实验

同一4B八头INT4权重，FP16激活/KV，1/4/8分支固定每头16tokens：

| 分支 | 每头TPOT | 每头token/s | 相对单头速度 | 合计token/s |
|---|---|---|---|---|
| 1 | 4.397ms | 227.4 | 100% | 227.4 |
| 4 | 5.081ms | 196.8 | 86.55% | 787.3 |
| 8 | 5.685ms | 175.9 | 77.34% | 1407.1 |

64tokens/head对照也得到约86.60%/78.03%的4/8头单头效率。该“1头AR”是同一多头权重的content分支，用于隔离运行时开销，不是另训普通AR JSON模型。测试强制等长忽略EOS，不代表真实调用自然输出长度；没有复现论文93%效率。

公共前缀prime + `prefix_match_unit=1`试验中，各分支只需新算head marker，前缀命中中位数99.844%；这证明公共状态先物化再分叉可实现。它不是原生prefill-only API，prime产生并丢弃一个token，且空闲单组E2E未总胜过同时提交；不能仅凭命中率声称海量并发吞吐已达最优。

### 14.3 最新H200频率：如何与能力报告组合

用户/速度工作线报告：**35B-A3B单H200接近16Hz**。如其定义为单请求从输入就绪到所需各头全部自然停止并组装完成，则对应约62.5ms/次，是后续持续交互的有用参考。本文未取得该次原始计时回执，暂不把16Hz与上表质量run绑定，也不填造TPOT、prefill、P50/P95或功耗。

应由速度工作线随报告补充：checkpoint及权重/计算/KV格式、context长度、图像与content开关、实际head数量、各头自然输出长度、warmup/冷热态、cache命中与新增prefill、客户端/引擎计时边界、并发、样本数及P50/P95。

一次真实调用完成时间由**最后一个必要head到达自身终止标记**决定。不同head启动时间、排队、prefill和CPU组装也要按计时定义计入；不能只报function首token，不能用总head token/s代替调用Hz。

397B-A17B在8×H200达到接近16Hz是下一步可验证的假设。MoE激活参数、显存带宽、多卡通信、TP/EP、routing、prefill与最长head长度都会影响结果；八卡与总参数比不能线性推出同速。当前已经有397B八卡H100 FP8/BF16功能与质量回归证据，尚没有本文可引用的8×H20016Hz证据。

### 14.4 关键缺口：同基座、强配置AR的任务级对照

现有单头TPOT与单独的16Hz报告，还不能回答“同一35B用普通JSON工具调用，准确率相差多少、完整请求慢多少”。下一张关键图应是同一批800题上的**完整调用准确率—真实E2E延迟**，并给出P50/P95、缓存条件与失败率。

AR侧使用同一原始Qwen3.6-35B-A3B基座，开启前缀缓存、紧凑且语义完整的schema，使用官方工具调用模板；在独立验证集比较原生工具调用、紧凑JSON及可用的约束解码，展示实测Pareto强配置。SimpleTool也使用语义等价输入，两侧实际缓存命中与新增prefill须记录，不能仅凭开启APC声称同条件。

该主对照比较真实可部署系统；要将差异进一步归因于并行架构，还需匹配训练数据的AR-SFT版本。不能强迫只学过多头协议的checkpoint输出JSON，再把它当最强AR，也不能用之前content单分支的TPOT替代正常完整工具调用。

AR总生成预算应覆盖完整调用，不能把SimpleTool每头128tokens与AR总共128tokens简单对齐。两侧自然停止、全量质量同scorer，新上下文与热前缀分开；必要时比较双方共同正确子集，以排除快速答错带来的延迟偏差。SimpleTool一次调用的结束仍取最晚必要head完成时间。

详细协议与测速交接：[35B同基座AR对照](AR_BASELINE_PROTOCOL_35B_20261113.md)。当前尚无该实验成绩，图表单元格保留待测；不将历史643/800与另一轮16Hz合成新的联合质量/延迟点。

## 15. 从现有数据可作出的能力陈述

可以直接引用的说明：

> SimpleTool将结构化调用拆为共享模型的函数分支与参数分支，分别自回归、并行解码。本轮在冻结的中英800题诊断上完成7个尺寸20组配置评测：5%训练版本的完整调用正确率从0.8B的37.625%逐步提升到35B-A3B的80.375%、122B-A10B的83.5%及397B-A17B的85.25%。在同一公开来源过滤/评分口径下，5%4B的INT4版本为4310/4786（90.05%）。继续增加当前训练数据比例时，小模型总分已出现边际收益平台，但较大基座整体仍提升高难和参数质量。云端/手机并行解码与397B FP8/BF16路径已有运行和回归证据；视觉工具选择及合成企业单据抽取也已完成受控探针。

能力结论的边界：

- 数据饱和指当前配方与分布的边际收益平台，不能推到所有大模型、所有更优数据或所有任务。
- 参数scaling指已有配置的经验趋势，不是控制变量完备的scaling-law拟合。
- 诊断800、公开来源4786和视觉5例分别代表不同证据层级，不应拼成一个准确率。
- 本轮主要为单调用、多候选、多参数；不证明多调用路由、实时闭环控制、机器人安全或工具执行成功。
- 16Hz为速度工作线最新报告，待其原始回执定义；397B8×H200同速仍待测。

## 16. 本轮之后更值得投入的方向

1. 固定5%作为主要预算参照，优先做高难变换、跨角色/跨头绑定、数组列一致性及历史状态恢复的定向数据对照；0.8B仍可参考20%点。
