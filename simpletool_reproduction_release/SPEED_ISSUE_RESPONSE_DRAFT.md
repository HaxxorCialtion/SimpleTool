Thanks for asking. We have published the recovered accuracy scripts and exact benchmark snapshot, together with pinned checkpoint information, raw model outputs, and latency scripts in `simpletool_reproduction_release/`.

To clarify the paper: the reported **16 Hz was measured directly on BFCL-v3**, not on the game/arm/avatar demo scenarios. We have now added a separate public-checkpoint BFCL-v3 single-turn measurement on an RTX 4090 48 GB. It processes exactly one question at a time; only the output heads belonging to that question run in parallel. Heads stop on `<|null|>` or a defined closing tag, with special-token skipping disabled for stop matching.

For `RT-Qwen3-4B-AWQ` (v1), the new measurement covers 1,880 capacity-supported questions from six released BFCL-v3 single-turn subsets. Mean complete local generation latency is **74.61 ms / 13.40 Hz** in an ordinary sequential traversal, **99.74 ms / 10.03 Hz** when resetting the prefix cache before each question, and **65.57 ms / 15.25 Hz** when the identical question is generated once before timing. The last setting is a favorable warm-cache diagnostic that excludes priming from request latency, not first-time query throughput. We do not claim that this run exactly reproduces 16 Hz under ordinary traversal.

We include every eligible question in timing, including incorrect outputs, one length-capped call per mode and two inputs without usable GT. All exclusions, per-head token counts and stop reasons, p50/p95 values, configuration and raw timings are available in `BFCL_SPEED_PROTOCOL.md` and `reports/bfcl-speed-4090/v1/`. The card has 48 GB; we have not measured a retail 24 GB card. This local timing excludes HTTP/network and actual tool execution. A matched autoregressive speedup baseline is also not included.

The previous three-scenario v2 demonstration remains a supplementary experiment with its own recorded settings. Full v2 BFCL accuracy and training code are not part of this release; the training-code publication schedule remains to be confirmed.
